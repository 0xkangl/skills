# Database Migration Safety Convention v1.0

> Applies to: 所有带持久化的模块（与语言/迁移工具无关） | Goal: 让 schema 变更在**有流量、有旧版本代码在跑**的生产环境里安全落地

For the full convention index, see [../SKILL.md](../SKILL.md).

本篇只讲**语言无关的生产安全实践**。具体迁移工具的用法（golang-migrate、Prisma、Alembic、Diesel 等）见各 `references/<lang>/<lang>-tools.md`。

迁移之所以危险，是因为它同时踩中三件事：**改的是唯一一份不可重建的状态**、**执行时旧版本代码还在跑**、**出错时没有「重启一下」这种退路**。下面所有规则都是从这三点推出来的。

## 1. 铁律

- **已在任何共享环境（staging / 生产）跑过的迁移，绝不修改**——改它意味着不同环境的 schema 历史产生分叉。要改就新加一个迁移。
- **生产只前滚**。回滚靠**新写一个前向迁移**，不靠 `down`。`down` 脚本只服务本地开发；把回滚寄托在生产执行 `down` 上，等于假设一个从未被演练过的路径能在事故中一次成功。
- **DDL 与 DML 分开成两个迁移**。结构变更与数据回填混在一个事务里，失败时你既不知道结构改到哪、也不知道数据填到哪。
- **用生产量级的数据测迁移**。在 1000 行的表上瞬时完成的操作，在 1 亿行上会锁表几十分钟。行数是这里唯一重要的变量。
- **迁移与发布解耦**：迁移必须能在**新旧两版代码同时在跑**时安全存在——滚动发布期间这是必然状态，不是边缘情况。

## 2. 加字段 / 加索引

- 新增列必须 **nullable 或带 default**。加 `NOT NULL` 且无 default 会触发全表重写并长时间持锁。
- 加索引用**并发方式**（PostgreSQL 的 `CREATE INDEX CONCURRENTLY`、MySQL 的 online DDL）。注意 `CONCURRENTLY` **不能在事务块内执行**——多数迁移工具默认把每个迁移包进事务，需要显式关掉。
- 加约束（外键、check）先以 `NOT VALID` 加上、再单独 `VALIDATE`，避免加约束时全表扫描持锁。

## 3. 改名 / 改类型 / 删除 —— expand-contract

**绝不原地改名或原地改类型**。旧版本代码还在读写旧列，原地改等于让它立刻崩。分三步跨越至少两次发布：

1. **Expand**：加新列，双写（代码同时写新旧两列），回填历史数据。此时新旧两版代码都能正常工作。
2. **Migrate**：读切到新列，确认无残留读旧列的路径（含离线任务、报表、其它模块仓）。
3. **Contract**：**先发布不再引用旧列的代码，再删旧列**。顺序反了就是一次生产事故。

删除同理：**先删代码，后删列**。中间至少隔一个稳定发布周期。

## 4. 数据回填（backfill）

- 回填走**独立迁移或独立任务**，不与 DDL 同事务。
- **分批提交**，每批限制行数并让出锁（如 `LIMIT n ... FOR UPDATE SKIP LOCKED` 循环 + 逐批 `COMMIT`）；一条 `UPDATE` 扫全表会长时间持锁并撑爆 WAL/undo。
- 回填必须**可重入**：中断后重跑不能产生重复或错误结果（用条件更新或幂等标记，别依赖「只跑一次」）。

## 5. 破坏性变更的判定

以下都是**破坏性**变更，须走 expand-contract 或版本化，不可直接上：删列、改列名、改列类型、收紧可空性、收紧枚举取值、加唯一约束、改变既有列的业务语义。

**在单个模块里改了字段名而不改契约，即使该模块测试全绿，它依然是破坏性变更**——绿灯只证明这个模块自洽，证明不了它的消费者还能用。

## 6. 上线前检查清单

- [ ] 该迁移未在任何共享环境跑过（否则新加一个）。
- [ ] DDL 与 DML 已分离；回填分批且可重入。
- [ ] 新列 nullable 或带 default；索引并发创建且未被包进事务。
- [ ] 破坏性变更已拆成 expand-contract，且「删列」排在「删代码」之后。
- [ ] 在生产量级数据上验证过执行时长与锁影响。
- [ ] 新旧两版代码在滚动发布期间都能正常工作。
- [ ] 前滚修复方案已想清楚（不是「跑 down」）。
