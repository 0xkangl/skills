# 仓库与 Git 工作流规范

适用于仓库初始化、CI 配置、忽略规则维护和 Git 写操作。项目已有分支、提交和发布约定优先；本规范不授予额外操作权限。

完整索引见 [SKILL.md](../SKILL.md)。

## 分支与操作范围

- 新项目没有约定时默认使用 `main`；已有项目沿用默认分支，不仅为统一命名重命名分支。只有项目采用 `release` 分支时，才按其稳定版本流程使用，不额外创建。
- 写操作前检查当前仓库、分支及已有改动。用户要求修改文件不代表要求暂存、提交、推送或部署；需要这些操作的明确授权，已经明确授权的同范围操作不重复确认。
- 删除、覆盖式恢复、清理、历史改写、rebase、强制推送、tag 和 release 等操作，必须核实具体目标、已有授权及恢复方式；不以命令名称代替风险判断，也不把所有 Git 命令一律视为同等风险。
- 推送前确认远端、分支与可能触发的 CI / 发布行为。新的生产或第三方影响超出原授权时，暂停相关操作并说明。

## 暂存与提交

- 按明确范围暂存；核对暂存差异，避免把用户原有改动、临时文件或敏感内容一并提交。
- 提交前完成项目要求及与改动相关的检查，并按 [项目文档规范](project-documentation.md) 同步受影响的文档；没有变化的文档无需制造提交。
- 同一提交围绕一个可说明的目的，代码与必要的测试、文档保持一致。提交信息遵循 [Conventional Commits](conventional-commits.md)。
- 提交语言、署名和共同作者信息遵循用户及项目约定；不能把第三方参考中的中文或禁止署名偏好自动套用到所有仓库。

## GitHub Actions 持续集成

- 使用 GitHub 托管的项目，应根据实际工具链在 `.github/workflows/` 配置持续集成检查，覆盖项目适用的构建、测试、lint 等检查；复用本地已有的检查命令，不为套用模板引入未采用的工具。
- 按项目分支与协作方式设置 PR、push 等触发条件，已有 workflow 优先维护。初始化时技术栈或检查命令尚未确定，待确定后再生成可运行的 workflow，不预填占位命令。
- 需要自动部署或发布时，按[部署规范](deployment.md#7-ci-集成)配置对应 workflow；仅执行持续集成检查不要求增加部署步骤。
- 工具链、检查命令或触发方式变更时，同步 workflow 与受影响的项目文档。

## 忽略文件与配置模板

- 按项目实际工具排除依赖安装目录、构建产物、缓存、系统临时文件、真实本地环境配置，以及含个人状态或凭据的编辑器和 AI 工具文件。
- 不笼统忽略所有编辑器或 AI 配置目录：共享任务、项目技能、规则、配置模板等可复用内容可按项目约定纳管；个人会话和凭据应排除。
- 不含密钥的 `.env.example`、`.env.*.example` 等模板允许提交；若宽泛忽略规则覆盖它们，应添加有效例外并检查实际匹配结果。模板内容遵循 [配置规范](configuration.md)。
- 使用项目临时目录时排除其中的可丢弃内容，正式运行与构建不能依赖未纳管的临时文件。清理边界遵循 `engineering-guidelines` skill 或宿主的适用要求。
- 忽略规则不会自动移除已经跟踪的文件，也不能消除 Git 历史中的密钥。发现此类情况时，说明实际跟踪状态和影响，按授权处理索引、凭据轮换及必要的历史修复，不把新增忽略规则报告成泄露已解决。
