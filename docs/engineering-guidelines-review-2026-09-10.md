## 结论与证据边界

保留范围、授权、已有改动保护、根因和结果验证；收敛通用思考口号、绝对化设计禁令及无差别流程。新模型的能力提升支持减少过程规定，但不证明工程约束可以全部删除。

必须区分三层：模型能力和训练倾向、产品或 Agent 宿主注入的系统规则、用户维护的技能与项目约定。公开文档只能支持已披露的行为和规范，不能据此声称掌握完整内部提示词、推理算法或每次执行的保证。Anthropic 明确说明，公开的网页与移动端系统提示词更新不适用于 Claude API。[系统提示词适用范围](https://platform.claude.com/docs/en/release-notes/system-prompts/overview)

## 现有规则逐项处置

下表中的“纠正”是对原文适用范围的工程判断；“冗余”不等于模型永不失误；“过时”主要指与当前模型协作方式不匹配的过程规定。

| 原规则或内容 | 维度 | 处理及原因 |
|---|---|---|
| 开头适用于所有模块和开发工具 | 范围过宽 | 定位为代码实施默认准则；description 描述触发场景，不重复整套方法 |
| 阅读相关实现、项目和下级规则 | 保留、澄清 | 聚焦适用目录与相关文档；明确宿主层级，不以本技能自行重定义平台权限 |
| 核实文件、函数、flag 是否存在 | 保留、补充 | 增加安装版本和一手资料；名字熟悉不代表当前接口正确 |
| Don't assume；每个假设都显式陈述 | 绝对化、冗余 | 允许依据上下文解决常规可逆细节，只报告影响结果的假设 |
| 所有解释都列出、问题一次问完且不得部分开始 | 过时、执行冲突 | 关键歧义才提问；只暂停依赖答案的工作，不重复已决定事项 |
| 提出更简单方案、适当反对 | 合并 | 合入设计成本和基于证据的分歧处理，不要求每次枚举所有方案 |
| 无额外功能、无推测性配置 | 保留、合并 | 完整实现当前要求，新增结构必须服务具体需要 |
| 禁止单次抽象 | 不适合作为绝对规则 | 单次使用也可能需要隔离或职责边界；改为判断实际必要性 |
| 不处理不可能场景 | 歧义、安全边界 | 只信任已核实内部契约，保留外部输入、网络、数据失败处理 |
| 证明标准库和所有已有依赖都不能解决 | 过度举证 | 检查适用性、说明具体收益，避免不必要的穷尽论证 |
| fetch / axios、date-fns / moment 固定示例 | 冗余、易误导 | 合并为复用现有能力；是否重复需看具体需求，而非仅凭库名判断 |
| 资深工程师会不会觉得复杂 | 泛化自问 | 删除；可检查的标准是需求、现有结构和成本 |
| 不改周边、不重构没坏的代码 | 保留、修正范围 | 禁止无关改动，允许任务本身需要的重构；补充编辑前检查工作区 |
| 清理本次孤儿代码、不删除已有死代码 | 保留、合并 | 纳入改动边界；“所有改变都对应需求”的重复口号不另占段落 |
| 所有多步任务写三步计划 | 过度流程 | 复杂或后果重大的变更才要求简要计划，不强制模板或计划文件 |
| 写测试再通过的三个示例 | 重复、流程过窄 | 保留可验证目标；允许复现、现有测试、诊断追踪和产物检查等合适证据 |
| Loop until verified | 缺少结束与受阻条件 | 明确必要检查通过即交付；有新证据才扩大检查；受阻则交付独立部分并说明缺口 |
| Evidence before assertions | 保留 | 这是交付可信度要求，不能用“模型更可靠”替代 |
| 退出码 0 但无输出就是失败 | 错误概括 | 判断预期效果；无匹配、静默成功或幂等无操作可能正确，写错目标则不能算成功 |
| 脚本自己的自检不可信 | 过度概括 | 保留必要的产物或消费者检查，不否定所有进程内验证 |
| 搜索不可用不代表不存在 | 保留、合并 | 纳入事实核验，注明不可达来源和未确认范围 |
| 第一性原理、追根因 | 能力重叠、保留实质 | 去掉口号，改为复现或具体追踪、验证失败路径、无新证据时调整假设 |
| 不允许跳过测试、添加旁路 | 保留、澄清 | 禁止为通过而掩盖问题；有意改变契约时允许更新过时测试 |
| Facts over feelings；被质疑时反问 | 重复、对话方式僵化 | 合并为依证据纠错和说明分歧，不要求为了反对而提问 |
| production-grade；忽略实现时间成本 | 不合理，非新模型独有问题 | 综合正确性、维护、运行和实现成本，避免过度设计 |
| 注释默认简体中文 | 个人偏好，非工程通则 | 本技能只要求遵循项目风格；用户的中文偏好仍由全局或项目指令负责 |
| 简短、不要前言 | 表达过粗 | 结果先行，保留必要进度、验证和限制，防止长工具链完全静默 |
| imports / types / edge cases 检查表 | 重复、无差别清单 | 合入相关风险与项目必需检查，不要求每个语言与改动都套同一表 |
| 任何既有 API 都不能破坏 | 缺少授权例外 | 默认兼容；明确要求改变契约时同步调用方、测试及相关文档 |

“先一步步思考”不需要作为通用触发咒语。OpenAI 的推理最佳实践说明内生推理模型无需额外 CoT 提示；该页面主要举旧 o 系列例子，因此只参考这一原则，不把其中旧模型分类或参数要求迁入 Astra。Claude 当前指南也建议避免人为固定推理步骤。[OpenAI 推理最佳实践](https://developers.openai.com/api/docs/guides/reasoning-best-practices)、[Claude 当前提示指南](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

原文没有要求公开完整思维链，不能把它误报为已有问题。此次只是将“思考口号”换成可观察验收条件；说明关键理由、证据和权衡仍然必要。

## 用户提供的他人指令：取舍

| 内容 | 处理 | 原因 |
|---|---|---|
| 明确指令即授权、持续推进、等待时做独立工作 | 吸收核心机制 | 与当前模型指导一致；授权限定于已有范围，并保留宿主权限要求 |
| 因规则暂停时给出文件与原文 | 吸收 | 方便识别真正的要求和 Agent 自行扩大解释 |
| 证据先于结论、性能收益提供前后数据 | 吸收 | 将可信交付落实到可以复核的证据 |
| 实现简单、按风险验证、保护用户改动 | 合并入既有章节 | 不另建同义规则集 |
| Bug 固定两轮失败后停止 | 不照搬次数 | 次数无法跨任务泛化；改为没有新证据时重新诊断 |
| 外部接口必须逐字段比对并一次改完 | 吸收证据原则，不强制全量流程 | 定位已确认差异优先；并非所有接口问题都来自请求字段，也不能保证一次解决 |
| 架构、schema、CI/CD、依赖等操作的授权要求 | 不照搬完整分类清单 | 参考指令已明确“已授权时不重复确认”；需取舍的是通用技能与专项规则的职责，而非把参考指令误读为要求反复审批 |
| AGENTS 为唯一正文、CLAUDE 为兼容入口 | 不纳入 | 本仓库明确采用相反入口；这是仓库制度，不是模型升级事实 |
| 强制 README / ROADMAP 三文档、20 条历史、时间戳 | 不纳入 | 应遵循项目现有制度，不为工程技能制造强制产物 |
| 中文标点、双连字符、绝对路径、提交中文与签名 | 不纳入 | 属于个人或渲染环境偏好，不能归因为新模型所需 |
| Computer Use、macOS open、Cloudflare、临时目录、Git 分支与发版 | 不纳入 | 属于工具、操作系统和项目专属工作流，应由对应规则负责 |
| Goal 文件、逐项多 Agent 施工清单 | 不纳入 | 属于显式长期任务机制；普通编码不需要自动创建 Goal 或强制委派 |

## 模型已具备什么，仍需约定什么

- **已有能力，可减少重复教学：** 推理、代码理解、方案构造、自我检查与长任务推进。保留目标、上下文和可检验结果即可，不规定完整思考路径。这是设计依据，不是逐条行为保证。
- **宿主可能已经覆盖：** 工具调用格式、指令层级、审批、思维链保护、上下文压缩、模型参数与委派工具。技能只保留必要的范围说明，不复制整套运行时手册。
- **不能靠能力推断：** 用户允许改哪些内容、是否要提交发布、仓库的契约和验证入口、已有未提交改动的归属、当前事实及真实工具结果。
- **不写入常驻文件：** 模型发布列表、价格、上下文长度、固定 effort、API thinking block / cache 规则。这些随版本和宿主变化，应在涉及模型配置的任务中查询。技能正文保留跨模型稳定决策标准。

| 场景 | 新规则应导致的行为 |
|---|---|
| 用户已要求修改，缺少一个可按既有风格决定的细节 | 继续实施，报告有影响的假设，不重复确认 |
| 数据迁移的目标环境存在关键歧义 | 询问目标，先完成不依赖环境的分析与准备，不猜测执行 |
| 修复小错误，发现无关旧 bug | 完成本次修复与相关验证，仅报告无关问题 |
| 用户明确要求破坏性 API 重构 | 允许改契约并同步受影响内容，不被“永不破坏 API”阻塞 |
| 生成器第二次运行没有改动 | 检查目标已满足，将合法幂等无操作与写错路径区分 |
| 网络不可达、测试工具缺失 | 说明缺失证据，完成独立工作，不声称不存在或已经通过 |
| 全部相关检查通过 | 交付，不为了形式继续扩大测试 |
| 用户只要求审查或诊断 | 提供发现与依据，不自行实施修复 |

后续要证明行为改善，需在相同仓库快照、工具权限、模型版本和 effort 下，对旧版与新版运行同一批任务，比较完成率、重复确认、越界改动、验证有效性、时延与 token 消耗。没有这类对照实验，不能声称本次修改已提高模型性能或消除所有失误。
